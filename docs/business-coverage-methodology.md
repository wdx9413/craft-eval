# 业务覆盖方法论：从业务模型派生用例，并论证充分性

本文回答两个问题：**业务用例从哪里来**（牵引），以及**凭什么说测够了**（充分性论证）。
通用标签（category/risk/difficulty）能统计"标了没有"，但回答不了"业务上该测什么"。
方法论的载体是**业务模型声明**（suite 的 `business` 字段）+ 派生检查 + 变异验证；
它论证的是"你声明的业务模型被覆盖了"，**不能**证明业务模型本身完备。

## 五个透镜

### 1. 不变量（Invariants）

业务规则里"无论输入什么，永远为真 / 永不为真"的断言。

- 派生规则：每条不变量至少派生 **1 个正例**（合法输入满足它）+ **1 个负例**（试图构造反例的输入）。
- 例：金融——摊销末期 balance 应为 0；利率为 0 时不得除零。电商——券后应付金额 ≥ 0。
- 失效边界：不变量枚举不全时，覆盖再高也只是"测了你知道的"。不变量的完备性只能靠事故回流与对抗测试逼近。

### 2. 生命周期（Lifecycle / 状态机）

业务对象有合法迁移（订单创建→支付→发货→退款→关闭）。每个**合法迁移**一个用例，
每个**非法迁移**一个负例（未支付就发货必须被拒绝）。

- 充分性判据：状态机中不存在"从未被任何用例触达的迁移"。
- 失效边界：并发、超时、部分失败造成的隐式迁移不在显式状态机里，需要单独补时序用例。

### 3. 边界与等价类

经典测试理论绑定业务参数：券门槛 199/200/201、利率 0/负/极大、库存 0/1/-1。

- 派生规则：每条数值规则至少一个"恰好等于边界"的用例。
- 失效边界：等价类假设类内行为一致；对非纯函数（时间、随机、外部状态）不成立。

### 4. 对抗与合规

对 Agent 类被测对象最重要：提示注入（商品描述里藏指令）、资质编造（无检测报告却宣称功效）、
越权工具调用（`tool_call called:false` 负例）。

- 派生规则：每条合规/安全声明至少一个"诱导违规"的对抗用例。
- 失效边界：对抗语料是开放集合，通过不等于安全；这是防弹测试而非证明。

### 5. 事故回流（Incident regression）

每个真实事故/线上缺陷必须回流为一个**留出集**用例，并引用来源。

- 充分性判据：留出集增长率与业务变更率同向；任何一次事故都没有对应用例即为缺口。
- 这是唯一能证明"评测集随业务成长"的判据。

## 充分性论证：变异分数

用例数量不构成充分性论证。业界的通行做法是**变异测试**：向被测系统注入 N 个已知缺陷，
统计评测集能抓到几个：

```
mutation_score = 被抓到的注入缺陷数 / 注入缺陷总数
```

- 抓不到的缺陷 = 用例盲区，回流为新用例后重测。
- 流程闭环：业务模型 → 派生用例 → 变异验证 → 缺口回流 → 事故回流。
- **诚实的边界**：mutation score = 1 只说明"声明的缺陷都被抓到"，不说明评测完美——
  注入集合本身也是人工枚举的。方法论的落点是"盲区可见、可回归"，不是"无盲区"。

## 在 craft-eval 中的落地

1. suite 声明 `business`（见 README 的 business 合同）：实体、不变量、规则、事故来源。
2. `audit` 派生检查：每条不变量/规则是否被 ≥1 个正例与 ≥1 个负例引用；未触达的生命周期状态。
3. `coverage` 把维度统计改为"业务模型派生维度 + 通用标签"并列。
4. `mutation` 命令：给定注入脚本目录，逐个应用到 baseline 副本上跑评测，输出 mutation score 与幸存缺陷。
