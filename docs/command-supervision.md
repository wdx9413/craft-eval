# 命令监护与执行器崩溃

目标：评测执行器退出或被强杀时，已经启动的可信本地命令及其同组后代能够被清理。保留现有退出码、信号、输入输出、取消和超时语义，不重放任何任务。

执行器不能在自己的 SIGKILL 处理器中收尾。主执行链的适配命令、评分脚本、模型裁判和用例服务分别由独立 Node 监护进程启动；监护进程与执行器保持专用 IPC。实际命令拥有独立 POSIX 进程组。命令退出时监护者先清理该组，再结束；执行器消失或取消导致 IPC 断开时，由仍存活的监护者清理命令。stdin/stdout/stderr 通过继承文件描述符传递，不把输出搬到 IPC 队列中。额外 Node 启动会增加小命令的开销，必须通过既有超时和吞吐回归检查。

实际命令退出或启动失败会生成独立的 `command-exit` / `command-error` 终态消息。监护进程自身退出不能替代此回执；缺少回执时作为监护错误处理，不能用监护者的退出码满足用例。Craft worker 丢失整次评测的终态回执时，保存为 unknown；相同 operation_id 返回旧状态，不自动重发。

监护进程使用受控的 Node 环境启动，命令自己的环境通过启动消息传入，不能通过命令的 NODE_OPTIONS 预加载到监护者。不会把历史 PID 存盘后盲目杀进程，也不会默认自动恢复或重发执行。

验收：真实执行器 SIGKILL、IPC 断开、正常退出、主动信号、缺失命令、监护启动失败、取消、超时、洪泛、stdin 与环境兼容；安装包中的监护入口必须完整。环境依赖探测与裁判校准也复用同一监护链，分别保留 5 秒和 60 秒默认时限；探测不收集输出，校准收集有界输出并接受取消。命令主动脱离进程组、监护进程本身被强杀、整机掉电和 Windows Job Object 仍是单独边界，不可宣称已被本方案覆盖。

依据：[Node 23 child_process 文档](https://github.com/nodejs/node/blob/v23.11.0/doc/api/child_process.md)描述独立进程、stdio 继承和 IPC；[process 文档](https://github.com/nodejs/node/blob/v23.11.0/doc/api/process.md)描述 disconnect 生命周期。上面的监护设计是基于这些机制的实现选择，实际清理能力仍以目标平台进程测试为准。
