## Problem Statement

使用 craft-eval 的人现在能在固定环境下跑出**确定性证据**（退出码、文件状态、MCP 调用日志、脚本判分），也能审计用例质量、做变异测试、校准判分器。但一旦面对真实业务决策，会出现四个卡点：

1. **开放式产出无法判分。** 电商方案、合规文案、金融报告没有唯一正确答案，只能靠关键词匹配；关键词既漏判质量问题，也误伤合规声明中的引用。`model_graded` 接口存在，但没有可复现的金集、没有真实判分器示例，"这个判分器可信"无法证明。
2. **一个用例需要多个判分视角，但结论只有一个布尔值。** 合规不过、转化可用的情况会被压成一个 failed，读者不知道是谁投了反对票；两个版本对比时也看不出"某个判分器在两版之间摇摆"。
3. **失败证据默认销毁。** 失败用例的 stdout、轨迹、产物在 run 结束后被删除，想复核或改判分器重打分必须重跑（单 case 可达数分钟）；同时多轮重复里"2 过 1 挂"的用例被当成普通通过统计，不稳定用例会污染增益结论。
4. **看不出评测集是否随业务成长。** 只能发现"开发集提示原样出现在留出集"，回答不了"这一版新增了哪些用例""两个用例是不是换了措辞的同一道题""跨分区污染是否同源"。

对应地，业务对象覆盖也偏窄：已有技能、单函数 MCP、单轮 Agent，缺电商类 MCP 的规则边界、多轮 Agent 的人工确认路径、以及提示注入/越权这类对抗用例。

## Solution

把上述能力按六个阶段补齐，每个阶段都产出**可验证的 JSON 契约 + 回归测试 + 真实对象运行记录**，并保持三条既有原则不变：判分器外置（不在工具内引入模型 SDK）、gateway 证据不可伪造、环境缺失不等于产品缺陷。

1. **判分器可信**：版本化金集 + 校准门槛 + 真实判分器示例；未达标的判分器不允许产生"失败"结论。
2. **多判分器聚合**：用例声明判分策略（全部通过 / 任一通过 / 加权），报告按判分器分组并列出分歧。
3. **证据自留 + 不稳定检测**：失败自动保留证据；多轮 verdict 不一致标记 flaky，并从增益证据中排除。
4. **数据集治理**：suite 版本链、版本差异命令、近似重复与跨分区同源检测。
5. **业务对象补全**：电商 MCP 规则矩阵、多轮 Agent 确认路径、对抗负例。
6. **报告与边界**：覆盖矩阵按业务模型派生，HTML 报告具备决策所需视图，与 craft 主仓的职责边界成文。

## User Stories

1. 作为评测负责人，我想要一份版本化的判分器金集，这样我能在换判分器前后用同一批样本比较准确率，而不是凭感觉。
2. 作为评测负责人，我想要校准命令在准确率或一致性低于门槛时返回非零退出码，这样 CI 能拦住"判分器坏了还在跑"。
3. 作为评测负责人，我想要判分器未通过校准时用例记为"未判定"而不是"失败"，这样我不会把不可信的判分器当成被测对象的缺陷。
4. 作为评测负责人，我想要一个可替换真实模型网关的判分器示例，这样我不必从零写调用、超时、输出上限与错误解析。
5. 作为评测负责人，我想要判分器缺失凭证时明确报告缺失哪个环境变量，这样我能区分"环境没配好"和"判分器判错了"。
6. 作为业务评测设计者，我想要给一个用例挂多个判分器（合规、转化、可读性），这样一次评测就能覆盖多个业务视角。
7. 作为业务评测设计者，我想要声明"全部判分器通过才算通过"，这样任一视角发现违规都能阻止结论。
8. 作为业务评测设计者，我想要声明"任一判分器通过即可"，这样探索阶段不会因为严苛视角全盘否定。
9. 作为业务评测设计者，我想要按权重聚合判分器并设置最低分，这样能表达"合规权重更高"的业务判断。
10. 作为业务评测设计者，我想要报告按判分器分组展示通过/失败数与分歧用例，这样我能定位是哪个视角在反对。
11. 作为业务评测设计者，我想要两个版本对比时给出每个判分器的一致率，这样我能判断是"被测对象变了"还是"判分器不稳"。
12. 作为失败排查者，我想要分析报告把"判分器分歧"单独归类，这样我不必逐条读 JSON。
13. 作为业务评测设计者，我想要不声明判分策略时默认"全部通过"并得到提示，这样不会因为漏写字段而静默放宽标准。
14. 作为失败排查者，我想要失败用例自动保留标准输出、错误输出、轨迹与产物，这样我能直接复核而不用重跑。
15. 作为失败排查者，我想要"仅在失败时保留证据"的选项，这样通过用例不会撑大运行目录。
16. 作为失败排查者，我想要改完判分脚本后用已保留的证据重新判分，这样我能在秒级得到新结论。
17. 作为失败排查者，我想要对没有保留证据的用例明确提示"不可重打分"，这样我不会拿到一个看上去有效的旧结论。
18. 作为评测负责人，我想要多轮重复中出现"既通过又失败"的用例被标记为 flaky，这样我能识别不稳定用例。
19. 作为评测负责人，我想要 flaky 用例从配对增益样本中排除，这样增益结论不会被摇摆在两个版本间的用例污染。
20. 作为评测负责人，我想要分析报告把 flaky 单独聚类，这样我能优先修复不稳定的环境或被测对象。
21. 作为数据集维护者，我想要 suite 声明版本号与上一版摘要，这样我能追踪评测集的演化。
22. 作为数据集维护者，我想要一条命令输出两版之间新增、删除、修改的用例，这样我能在评审中聚焦变化。
23. 作为数据集维护者，我想要近似重复检测，这样换了措辞的同题不会被当成两个独立样本。
24. 作为数据集维护者，我想要跨分区同源检测，这样共享来源的提示不会让留出集名不副实。
25. 作为数据集维护者，我想要脱敏标记不豁免同源检查，这样"已脱敏"不会被误当成"已独立"。
26. 作为业务评测设计者，我想要一个可离线运行的电商 MCP 评测示例，这样我能验证商品查询、下单、库存扣减的规则边界。
27. 作为业务评测设计者，我想要券门槛 199/200/201 三个边界各有用例，这样边界条件不会被漏测。
28. 作为业务评测设计者，我想要库存不足与重复下单幂等的用例，这样失败路径与并发语义都在覆盖内。
29. 作为业务评测设计者，我想要一个多轮 Agent 评测示例，其中包含"未确认不得执行"的路径，这样人工确认门禁能被验证。
30. 作为业务评测设计者，我想要提示注入与越权的对抗负例，这样被测对象"照做恶意指令"会被判失败。
31. 作为业务评测设计者，我想要对抗用例的证据来自评测器侧的模拟服务调用日志，这样被测对象无法伪造"我没调用"。
32. 作为报告读者，我想要覆盖矩阵按业务模型（不变量、生命周期迁移、数值规则）派生，这样我能看出哪条业务约束没被用例引用。
33. 作为报告读者，我想要覆盖矩阵区分"未声明"与"声明未覆盖"，这样我知道该补标签还是补用例。
34. 作为报告读者，我想要 HTML 报告包含判分器视图、flaky 列表、业务覆盖矩阵与变异分数，这样我不必打开多个 JSON。
35. 作为报告读者，我想要数据缺失时报告显示"未测量"而不是隐藏区块，这样我不会把缺省当成通过。
36. 作为维护者，我想要一份成文的职责边界，说明本工具只产出证据、不授予发布权，这样两套评测代码不会口径分叉。
37. 作为新加入的维护者，我想要一份运行手册覆盖前置检查、跑测、看结论、重打分与常见失败，这样我能独立完成一次评测。
38. 作为 CI 维护者，我想要每个阶段都有可复现的验收命令与真实对象运行记录，这样评审时能确认"真的跑通"而不只是"测试通过"。

## Implementation Decisions

### 判分策略与判分器分组

- 用例新增可选字段 `judge_policy`，取值 `all_required`（默认）、`any`、`weighted`（含 `min_score`，范围 0..1）。
- 策略只作用于带 `judge` 字段的检查项；无 `judge` 的确定性检查继续沿用现有阈值语义。两组结论都通过，用例才 passed。
- 任一判分器返回错误 → 该组 inconclusive → 用例 inconclusive；`all_required` 下也不降级为 failed（不可信判分器不得制造失败）。
- 未声明策略但存在多个判分器时，默认 `all_required`，并在报告里给出 `judge_policy_defaulted` 提示。

```ts
type JudgePolicy =
  | { mode: 'all_required' }
  | { mode: 'any' }
  | { mode: 'weighted'; min_score: number };
```

### 报告契约

- 运行报告新增 `by_judge`（每个判分器的 observed/passed/failed/inconclusive 与失败用例）、`judge_disagreements`（同一用例内通过判分器与失败判分器名单）、`flaky_cases`（verdict 计数与 trial 数）。
- 对比报告新增 `judge_agreements`：同一 (case, trial) 在两个版本下该判分器判分相同的比例；无样本时为 `null`，不填 1。
- 失败归因新增 `judge_disagreement` 与 `flaky` 两个类别，与既有类别并列，聚类规则不变。

### 证据保留

- `--keep-traces` 由布尔扩展为三取值：`never`（默认）、`on-failure`、`always`。旧布尔写法继续可用，分别映射为 `always` / `never`。
- 落盘位置与现有结构一致，仅供人工复核与重打分；原始轨迹永不回读为判分证据。
- 计划文件记录实际取值；旧报告读回时把布尔映射为对应取值，不推断未记录的条件。
- 重打分遇到没有证据的用例输出 `not_rescorable: no_captures`，不复制旧结论。

### flaky 与增益

- 仅当 trial 数 ≥ 2 时判定 flaky；verdict 集合同时含 passed 与非 passed 即视为 flaky。
- 对比时 flaky 用例不进入配对样本，并在 `flaky_excluded` 列出；`skill_gain_supported` 额外要求该列表为空。

### 数据集治理

- suite 新增 `version`（语义版本）与 `parent_digest`（上一版摘要）；审计输出谱系，并对"父版本未提供、循环引用、声明新版本但内容未变"分别给出 finding。
- 新增版本差异命令，输出新增、删除、修改的用例与"父摘要是否匹配"；修改判定复用审计中已有的规范化内容摘要。
- 近似重复：规范化（全半角归一、小写、折叠空白）后取字符 5-gram、计算 Jaccard，默认阈值 0.9 可配置；仅对长度 ≥ 64 字符的提示生效，避免短题误报。
- 跨分区同源：同一来源同时出现在开发集与留出集时报告；`sanitized: true` 不豁免。
- 新增 findings 均为 warning 级，不阻断运行，但会出现在 `coverage.gaps` 同口径的清单中。

### 业务对象

- 电商 MCP 用驱动模式（被测 server 作为长服务，评测器作为客户端驱动）评测，不依赖外部 SaaS；库存、券门槛、幂等各有正负例。
- 多轮 Agent 用场景模式串联"澄清 → 确认门禁 → 执行"，确认门禁用本地审批替身表示，未确认路径必须失败。
- 对抗用例用评测器侧模拟 MCP 服务驱动，越权与注入的判定依据是评测器记录的调用日志（`called: false`），不是被测对象自述。

### 覆盖矩阵与报告

- 覆盖命令在现有维度之外新增业务维度：每条不变量（正例数/负例数/是否覆盖）、每条生命周期迁移（用例数/是否覆盖）、每条数值规则（各边界用例数/是否覆盖）；未覆盖条目进入 gaps。
- HTML 报告固定区块顺序：概要（含未判定数与 flaky 数、变异分数）、语言分布、判分器视图与分歧、flaky 列表、业务覆盖矩阵、逐用例详情。缺失数据显示"未测量"。
- 职责边界与运行手册作为唯一权威文档，README 只链接。

### 兼容性与安全

- 所有新增字段可选；未声明时行为与现状一致。
- 判分器仍为外部命令，工具内不引入模型 SDK；判分器输出仍按"严格 JSON、分数 0..1、超时与输出上限"解析，失败记 `judge_error`。
- 判分器校准结果只作为"是否允许产生失败结论"的门槛，不作为发布依据。

## Testing Decisions

**什么算好测试**：只验证外部可观察行为——命令退出码、报告 JSON 中的字段与数值、落盘证据目录是否存在、归因类别、比较结论。不测试私有函数、不测试内部调用顺序、不断言日志文案。每条新增行为至少覆盖一个"反例"（应当不被误判的情形），例如判分器报错不能被当成失败、脱敏不能豁免同源检查、单轮重复不能被判 flaky。

**测试模块**：

- 受控执行与判分：判分策略三模式、判分器错误、未校准判分器、环境缺失被判为未判定。
- 报告与归因：按判分器分组、分歧列表、flaky 列表、两个新归因类别。
- 证据与重打分：三种保留模式、仅失败保留的证据存在性、无证据时的不可重打分标记。
- 对比：判分器一致率、flaky 排除对增益结论的影响。
- 审计与覆盖：版本谱系三类 finding、近似重复两档阈值、跨分区同源、业务维度覆盖与 gaps。
- 命令层：新增差异命令与新增选项的错误提示（非法阈值、缺失参数、非法模式）。

**既有先例**：仓库已有大量同类测试可参照——受控执行与判分行为参照现有评测执行测试；审计 finding 参照现有审计测试；统计与对比参照现有对比测试；命令参数错误参照现有 CLI 测试；覆盖率门禁参照现有上下文审计与构建套件测试。新增测试沿用同一夹具风格（临时目录 + 最小套件/受试对象），不引入新测试框架。

## Out of Scope

- 不内置任何模型 SDK，不替用户选择模型或路由。
- 不做自动权重学习，判分器权重与最低分必须显式声明。
- 不做语义向量相似度检测，近似重复仅基于规范化文本的字符 n-gram。
- 不声称能证明"数据集未被污染"，只报告可观测的重复与同源。
- 不接入需要真实凭证的支付/物流 SaaS；业务 MCP 与对抗用例均离线运行。
- 不做在线仪表盘、持续服务或前端框架；报告是单个静态 HTML 产物。
- 不自动重试、不自动发布：重试属于实验编排语义，发布决策属于上层。
- 不把变异分数、覆盖矩阵或判分器校准结果当作发布许可。

## Further Notes

- 阶段划分、每阶段验收条件与当前代码事实基线已记录在路线图、现状基线、六个阶段文档、职责边界与运行手册中；本方案只补充"怎么做"的决策，不重复这些清单。
- 一条已知的上游限制：Codex Host 不暴露技能调用事件，因此用 Codex 跑技能评测永远拿不到触发级证据；该限制不会因为本方案改变，相关用例必须显式标注为不可判定而不是失败。
- 一条已知的被测对象问题：craft 主仓官方单进程全量测试存在跨用例状态污染（单文件通过、全量失败），本方案不修被测项目，只在报告里如实反映。
- 验收以"构建通过 + 相关测试全绿 + 至少一条真实对象运行记录"为准；仅测试通过不足以说明能力可用。
